# 有纪律的改码：全局理解 → 证据定位 → 根因修复 → 实证验证

本 skill 约束的是**过程**，不是某个具体技术栈。核心命题：

> **局部正确、全局错误**是本类工作最常见也最贵的失败模式。
> 一个"修好了眼前问题"的改动，可能引入一个更难发现的回归——
> 而后者往往在真实流量下才爆发。

以下每一条都标注了**代价**（不这么做会发生什么）。

---

## 0. 动手前的强制动作：建立全局心智模型

**不要一上手就改那一行。** 先回答这些问题，答不上来就不要动代码：

1. **这个模块在整个请求/数据流里的位置是什么？** 它的上游是谁、下游是谁？
   调用它的有哪几处（用搜索工具列出**全部**调用点，不要只看第一处）？
2. **有哪些共享状态？** 谁读、谁写、谁负责回收？跨哪些 goroutine/线程/进程？
3. **有哪些锁？锁的顺序是什么？** 每个临界区里做了什么（是否含 I/O、分配、
   遍历无界集合）？
4. **数据结构的生命周期与边界是什么？** 它会不会无界增长？谁负责清理？
   清理是在热路径上还是后台？
5. **这些值是从哪来的？** 配置？配置的默认值在哪推导？有没有第二处独立推导
   同一语义（两条路径会不会不一致）？
6. **有没有既有的、我该复用的机制？** （限频器、reaper、缓存、验证器……）
   重复造轮子通常等于造出第二个漏回收的 map。

**代价**：不理解全局就改动，等于在别人的不变式上打洞。本类项目里反复出现的
事故形态是——"局部修好了，但把它放到了热路径/锁内/无界增长的位置"。

> 具体做法：改动前用搜索工具列出目标符号的**全部**调用点与定义点，
> 读完整函数而不是几行；读同包内相邻文件（往往放着同一模式的其它实例）。

---

## 1. 定位必须靠证据，不靠猜测

**禁止**在没有可观测证据时给出因果结论。允许的定位手段（按强度排序）：

| 手段 | 说明 |
|---|---|
| 基线与对照 | 改前的二进制/提交与新代码跑**同一实验**，对比可观测输出 |
| 真实进程复现 | 起真实服务 + 真实流量，看日志/指标/响应，而不是只跑单测 |
| 剖析器 | CPU / mutex / heap / block profile，让数据指出瓶颈 |
| 最小复现 | 把现象压缩到最小可执行片段，确认它**单独**就能复现 |
| 静态推导 | 只有在上面都不可得时才用，且必须标注"待验证" |

**关键纪律：结论的方向对了，理由可能是错的。** 评审者或你自己给出的
"为什么"必须单独验证——理由错了意味着修法可能没打到真正的根因。

**代价**：靠猜测定位会修错地方。本类项目中真实的例子是：连续多轮都在优化
自己新写的业务锁，而剖析后发现瓶颈是一处**既有代码**里的日志打印抢标准库
全局锁，占了 80% 的锁争抢。**没有一次剖析，这个结论永远不会浮现。**

---

## 2. 修根因，不修症状

- 问："如果我只改这一行，同一类问题还会在别的输入/路径下出现吗？"
- 问："这个约束应该由**谁**保证？是调用方记得做，还是结构自带？"
  → **能被忘记的契约，一定会被忘记。** 把边界内建到数据结构里。
- 症状修复（把阈值调大、把日志删掉、把循环次数降下来）必须明确标注为
  权宜之计，并留下后续项。

**代价**：修症状会让同一个 bug 以另一个形态回来。真实例子：
把"每 5 分钟清空在途验证码"改成"留足余量"——余量是假设，不是保证；
正确做法是改成**只淘汰最旧的**，让"不作废在途数据"成为结构性性质。

---

## 3. 改动前评估全局连锁影响（本 skill 的重点）

对每一处改动，逐条过这个清单：

### 3.1 热路径
- 这段代码每请求都跑吗？每请求的成本是多少？
- 我加的操作是 O(1) 还是可能退化？会不会把 O(n)/O(n log n) 放进热路径？
- **有没有把工作从"后台"挪到了"前台"？**（反向也要查）

### 3.2 锁与并发
- 临界区里是否做了 I/O、内存分配、或遍历**无界**集合？
- 持锁时长随数据规模增长吗？（这决定高负载下会不会雪崩）
- 是否与别的热路径**共用同一把锁**？共用意味着"后台清理"也会阻塞在途请求。
- 有没有普通 map 被并发读写？（Go 下这是 `fatal error`，**直接终止进程**，
  不是普通竞态。）需要保护时用互斥锁或并发安全结构，并写并发测试。
- 有没有新增无同步的共享可变状态？

### 3.3 内存与生命周期
- **新增了长期存活的 map/缓存吗？它的 key 由谁控制、谁负责回收？**
  如果 key 来自请求（IP、会话、路径、UA），攻击者就能让它无界增长。
- 回收机制是"调用方要记得调"还是"结构自带"？→ 优先后者。
- 容量上限是否随某个**可配置项**线性放大？→ 必须有**绝对天花板**，
  否则一次配置调整就能把内存推到 GB 级，而配置界面不会提示。
- 清理策略会不会破坏用户可见的在途状态？（如让用户正在作答的验证码失效）

### 3.4 配置与兼容
- 我加的默认值是"安全阀"还是"目标值"？用错语义会导致默认配置就不安全。
- 显式写死一个值会不会**钉死**本该自动跟随的推导？
- 有没有第二处独立推导同一语义？两处会不会不一致（日志与实际行为不符）？
- 行为是否变更？→ 变更必须写进 CHANGELOG 的"升级注意"。

### 3.5 同一模式的其它实例
> **修完一处，立刻全局搜索同一模式。**

"长期存活 map 缺回收"在本类项目里出现过**四**次；"持锁遍历全表"出现过
**三**次。找到一处时，其余几处只是还没爆发。

**代价**：不查连锁影响，就会用一个新的、更隐蔽的 bug 换掉旧 bug。
真实例子：为消除"状态全丢"的抖动，把 O(1) 的整体重建换成 O(n) 遍历清理——
在攻击场景下遍历几十万条**且一条都删不掉**，变成每请求 O(n) 且踩在全局锁上，
**比它要修的问题严重得多**。

## 4. 实证确认"真的修好了"

### 4.1 回归用例必须能抓住旧行为
- 新写的测试要问："**在修复前跑它，会失败吗？**" 不会失败的测试不是回归用例。
- 对"性能/并发/内存"类改动，测试要断言**语义契约**（有界、不阻塞、精确删除）
  而不只是最终结果。

### 4.2 前后对比要用同一实验
- 改前/改后跑**同一个**压测或复现脚本，对比同一指标。
- 报告改进幅度时**必须标注测量条件**（并发数、数据规模、取样窗口、
  以及压测端本身是否已成为瓶颈）。
- 若收益没有完全转化（例如争抢降 70% 但吞吐只涨 10%），**查清并如实说明**
  限制因素，不要只报好看的数字。

### 4.3 契约边界要单独测
断言"最旧的 N 条必然全部被淘汰"这类**过强**断言会在边界上失败——
那不是算法错，是断言超出了实现提供的保证（例如按秒分桶后桶内无序）。
此时应**修正断言到真实契约**，而不是去迁就断言改坏实现；同时保留一个用例
覆盖"桶内不保证顺序"这一事实。

**代价**：不验证就宣布修好，等于把判断权交给运气。真实例子：
连续两轮都在报告"已修复"，而剖析显示锁争抢只降了一半——因为还有一处
同类日志打印没被处理。

---

## 5. 数字必须来自测量

- **注释、提交信息、评审回复里的任何量级数字都要有出处**：注明测量条件，
  或明确标注"估算/待验证"。
- 同一份产出里不得出现互相矛盾的数值。发出前自查一遍。
- **结果荒谬时先怀疑测量，而不是怀疑系统。**
  （真实例子：`uint64` 相减下溢得出"单条 4611686018427381 字节"的内存占用；
  换成有符号相减又因运行时状态得到负数——两次都该被"荒谬性"拦下来。）
- 用别人的测量值时，**注明是沿用而非自测**。

**代价**：一个没测过的数字会误导后来的人。真实例子：注释里写"实测 20ms"、
报告里写 36ms、实际 73ms——**三个值，两个是凭感觉写的**，而这段注释的
唯一用途就是给后来者做量级参考。

---

## 6. 回应评审：逐条独立验证，不无条件服从也不无条件反驳

对每条意见给出明确裁决，并**附上自己的证据**：

- **成立** → 认，并说明修法与代价。
- **不成立** → 用可执行证据反驳（日志、实测、代码路径），不要只说"我认为"。
- **方向对但理由错** → 分开展开：认可目标，指出理由的问题，然后给出正确修法。
- **证据不足** → 标注"待验证"，并给出验证方案，不要猜着表态。

**代价**：无条件服从会为了迎合而引入退化；无条件反驳会错过真问题。
真实例子：评审以"这样更根本"为由建议的做法确实更根本（认同），
但它给出的**理由**（"会溢出索引"）是错的——若照理由去改，会改错地方。

---

## 7. 收尾

- 复跑**全量**构建 / 静态检查 / 测试（不是只跑改动的包）。
- 格式检查若报错，先分辨是**真问题**还是行尾符导致的假阳性
  （用归一化副本验证），别整文件重写。
- 清理临时脚手架、探针、剖析转储、后台进程、仓库外临时目录。
- 确认工作区状态符合预期（该提交的、不该出现的）。
- 工作区里若有**未跟踪文件**，注意某些工具链会把它们记为 dirty
  （可能影响构建元数据与发布包）。

- [ ] 我修的是根因吗？同一类问题还有别的入口吗？
- [ ] 实时路径/锁/内存是否有新增的、随规模增长的成本？
- [ ] 新增的长期存活结构，回收责任在谁？能被忘记吗？
- [ ] 新上限会不会随配置线性放大？有绝对天花板吗？
- [ ] 行为变更是否已记入 CHANGELOG 与升级说明？
- [ ] 同一模式在别处还有几处？
- [ ] 我的回归测试**在修复前会失败**吗？
- [ ] 我报告的数字都有出处吗？互相一致吗？
- [ ] 我把"可能的新问题"如实写出来了吗（哪怕它超出了原始请求范围）？
